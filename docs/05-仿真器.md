# 仿真器技术说明

本文说明 `simulator/` 是怎么来的：哪些是从固件原样移植的、哪些是仿真器自己引入的、物理参数怎么定的、以及验证做到了什么程度。

对应的操作说明见 [simulator/README.md](../simulator/README.md)。

---

## 1. 为什么要做仿真

飞控代码里最容易出问题的地方不是"某个函数写错了"，而是**环路**：姿态环的符号对不对、相位裕度够不够、定高切入时的瞬态大不大、断链保护会不会误触发。这些问题在实物上只能靠试飞发现，而试飞的成本很高（摔机、找场地、看日志）。

仿真的价值在于：把固件那组 PID 增益放到一个可控的物理模型里跑，就能在几秒钟内看到环路是收敛还是发散，而不用真去摔一台飞机。

前提是**控制部分必须是同一份代码**——否则仿真的结论对真机没有意义。所以这里做的是移植，不是重写。

---

## 2. 固件算法移植：逐文件对应

`js/fw/` 下的每个文件对应一个固件源文件，逐行对应，包括符号约定和数值细节。

| 仿真文件 | 固件源文件 | 移植时保留的细节 |
| --- | --- | --- |
| `fw/pid.js` | `Common/pid/Com_PID.c` | 误差定义为 `测量值 − 期望值`（所以增益为负表示方向正确）；`isAngle` 时误差折算到 (−180°, 180°]；积分限幅与输出限幅"上限 ≤ 下限即不启用" |
| `fw/filter.js` | `Common/util/Com_Filter.c` | 一阶低通返回值时按 int16 截断（固件返回 `int16_t`）；卡尔曼的 Q=0.001、R=0.543；用单精度语义 |
| `fw/imu.js` | `Common/imu/Com_IMU.c` | 四元数一阶龙格库塔递推；加速度计 PI 补偿（Kp=0.8, Ki=0.0003）；`Q_rsqrt` 用位模式魔数 + 两次牛顿迭代；偏航 0.5°/s 死区；`asin` 入参 ±1 限幅 |
| `fw/state.js` | `Common/config/Com_Config.c` | 全部全局状态与 8 个 PID 实例、3 个卡尔曼滤波器 |
| `fw/flight.js` | `App/flight/App_Flight.c` | 角速度低通 / 加速度卡尔曼；3 组串级姿态 PID；X 字型混控；测距野值剔除；定高状态机（0/1/2）与互补滤波；电机限幅 0~1000 |
| `fw/comm.js` | 两个 `App/App_Communication.c` | 18 字节定长帧的组帧与解析；帧头/长度/累加校验和三级校验；连接判定；油门序列解锁状态机 |
| `fw/tasks.js` | `App/task/App_Task.c` | 任务周期 4ms / 6ms / 50ms / 10s；LED 灯效与"每 N 个灯控周期翻转一次"的引脚行为 |

### 传感器也按寄存器级还原

`sim/sensors.js` 里的虚拟 MPU6050 **输出的是原始 int16 LSB 值**，和固件经 I2C 读到的完全同级：

- 陀螺仪：`度/秒 × (65536/4000) + 零偏 + 白噪声`
- 加速度计：机体系比力 `a − g` 换算成 LSB，静止水平时 Z 轴读 ≈ 16384（1g）
- 零偏校准按固件流程走：先做静止判定（连续 30 次采样角速度变化 < 10 LSB），再取 255 次平均，最后扣掉 `MPU_ACCEL_1G_LSB`

这样做的意义：`Com_Filter_LowPass` 返回 int16 的截断行为、卡尔曼在整数尺度上的收敛过程、`normAccZ` 的 16383 量级——这些在"直接喂物理量"的仿真里都会失真。

### 定时也是还原的

固件用 `vTaskDelayUntil` 让飞控任务严格按 4ms 执行，PID 里的 `dt` 就取自这个周期。仿真器把模拟时间按 **0.5ms 时间片**推进，任务调度器用累积器按各自周期触发任务，所以：

- 飞控任务严格每 4ms 一次（实测：25.7 秒仿真时间触发 6430 次，6430 × 4 = 25720 ms）
- 通讯任务 6ms、灯控 50ms、电源 10s 同样精确

若把周期做错（比如按渲染帧率调用），那组 PID 增益的行为就跟着变了，仿真结论也就不再对应真机。

## 3. 物理模型（仿真器自己引入的部分）

固件里只有"给电机写 PWM"，没有飞机。`sim/dynamics.js` 补上这一层：

```
1. 电机一阶惯性      w += (cmd − w)·(1 − e^(−dt/τ))     τ = 22 ms
2. 推力              T_i = kT · w_i²                     推力 ∝ 转速²
3. 力矩              推力差 → 滚转/俯仰力矩；
                     螺旋桨反扭矩 → 偏航力矩：τ_z = Σ c_i·kQ·w_i²
4. 转动              欧拉方程 I·ω̇ = τ − ω×(Iω) − c·ω
5. 平动              升力 + 重力 + 气动阻力（水平/垂直分开给系数）
6. 四元数积分         机体系角速度 → 姿态
7. 约束              地面/楼顶/桥面碰撞、摩擦、硬着陆判定
```

### 电机位置与旋向不是随便定的

`dynamics.js` 里 `MOTOR_LAYOUT` 的取值是由**固件的混控方式反推**出来的：

```
横滚 +: leftTop + leftBottom      → 这两个必须在滚转轴两侧
俯仰 +: leftTop + rightTop        → 这两个必须在俯仰轴两侧
偏航 +: leftTop + rightBottom     → 对角同组，与另一对角反向
```

把这四条和"控制器极性必须构成负反馈"联立，电机的物理位置与旋向就唯一确定了（固件里的 L/R 只是命名，真正决定几何的是混控的分组方式）。这一点很关键：如果电机摆错，那三个姿态环在仿真里会直接发散——而这恰恰能反过来说明移植是自洽的。

### 加速度计要算"比力"，不是"自由落体加速度"

这是实现时踩到的一个坑，值得单独说。

加速度计测的不是运动加速度，而是**比力** `a − g`。静止在地面上时飞机的运动加速度为 0，所以读数应当是 **+1g**；如果按自由落体加速度（−g）去算，比力会变成 0g。

结果就是：在地面上时姿态解算拿到的加速度是零向量，归一化方向不确定，四元数的重力补偿朝错误方向修正，姿态估计发散；同时定高的重力基准 `staticAcc` 被标定成 0，一进定高就出现巨大的速度偏置，飞机掉高。

修法是用**速度的实际变化量反算加速度**（`(v − v₀)/dt`），地面接触力就自然被计入了：

```js
d.accelWorld.x = (d.velocity.x - vx0) / dt;   // 接触力也算进去了
```

改完之后静止在地面时加速度计读数 ≈ 16383（1g），姿态解算与定高都正常了。

## 4. 物理参数整定：让固件那组增益飞得稳

### 问题

固件的 PID 增益是按真实飞机整定的，而仿真器的物理参数（质量、转动惯量、推力系数、电机时间常数、转动阻尼）是仿真器引入的。**参数取得不合适，同一组增益在仿真里就会振荡甚至发散——那是模型的问题，不是固件的问题。**

一个具体的例子：最初把转动阻尼设成 `2.2e-5 N·m/(rad/s)`，速率内环的相位裕度只有十几度，表现是持续抖动。按桨叶诱导速度变化估算，真实的转动阻尼应该在 `3e-4` 量级，差了 15 倍。

### 做法：用数值搜索代替手算

`tools/tune.mjs` 在参数空间里搜索（粗搜 320 组 + 局部细化 625 组），判据是：

1. 三个姿态轴各施加一次 3 rad/s 的角速度扰动，**取最差轴**
2. 打分 = 收敛时间 + 峰值超调 + 收敛后的残余角速度/角度 + 悬停高度漂移
3. 发散、NaN、撞地直接给极高惩罚分
4. 加一条可用性约束：悬停油门必须落在手杆中段（430~700），否则一只手杆没有爬升余量，演示时不好飞

搜索过程中还修掉了测试台自身的一个缺陷：`Com_IMU.c` 的四元数是函数内 static 的，两次实验之间不清零会互相污染，导致结果不可复现——`harness.mjs` 现在会在每次建台时调用 `QC.imu.Reset()`。

### 结果

| 参数 | 取值 | 依据 |
| --- | --- | --- |
| `angularDrag` | 1.56e-4 N·m/(rad/s) | 与"桨叶诱导速度随转动变化"的估算（≈3e-4）同量级 |
| `motorTimeConstant` | 22 ms | 空心杯电机 + 小桨的机械时间常数范围 |
| `thrustCoef` | 6.965e-7 | 由目标悬停转速 440 反推：`4·kT·w² = m·g` |
| `inertia` | x/y 3.6e-5, z 6.5e-5 kg·m² | 回转半径 ≈ 2.6 cm，与 100mm 轴距的微四轴相符 |
| 悬停转速 | 440（对应油门 **629**） | 手杆中段偏上，上下都有余量 |
| 满油门推重比 | 5.17 | 微四轴常见量级 |

最终三轴表现：

| 轴 | 收敛时间 | 峰值 | 残余角速度 | 残余角度 |
| --- | --- | --- | --- | --- |
| 横滚 | 0.10 s | 1.8° | 0.0008 rad/s | 0.03° |
| 俯仰 | 0.10 s | 1.5° | 0.0016 rad/s | 0.01° |
| 偏航 | 0.11 s | 4.0° | 0.0023 rad/s | 0.006° |

也就是说：**固件那组增益在这个模型上是收敛的**，而且收敛得很快。这本身就是对移植正确性的一次交叉验证——如果某个轴的符号接反了，它会直接发散。

## 5. 验证做到了什么程度

### 5.1 无头自检（37 项，全部通过）

```bash
node simulator/tools/selftest.mjs
```

浏览器与自检用的是**同一份源文件**（Node 侧用 `vm.runInThisContext` 把那些普通 `<script>` 模块跑进同一个全局环境），所以不存在"测试版"和"发布版"漂移。

覆盖：快平方根倒数精度、2.4G 帧三级校验（含 8 个单比特翻转）、AHRS 收敛（带零偏）、三轴环路负反馈、解锁状态机、断链保护、定高环、未解锁严禁转电机。

### 5.2 浏览器实跑

用浏览器自动化在真实页面里验证过：

- 页面无 JS 报错，无 NaN（`attitudeDiverged` 计数为 0）
- 键盘通路：按 W 油门 0→570 且**松手保持**；方向键按下→松开后**精确回中到 500**；横滚极性映射正确（摇杆 905 → 通道 95）
- 完整飞行：解锁 → 爬升到 24 m → 前飞 → 悬停，姿态回到 ±0.2°，垂直速度 0.03 m/s
- 定高：漂移 0.00 m，受向下扰动 2.5 m/s 后 3 秒内拉回
- 链路：4287 帧发出，4263 帧通过校验，**24 帧被故意注入的比特错误全部被校验和拦下**，0 丢包
- 控制周期：25.7 秒仿真时间触发 6430 次飞控任务 = 严格的 4 ms

### 5.3 渲染检查

因为要确认"画面对不对"，做的是**像素级校验**而不是只看截图：

- 绘制调用 55 次、三角形 5.3 万个、几何体 21 个、贴图 7 张 → 场景确实有内容
- 把渲染帧读回来降采样成 32×14 色块图：上方天空渐变（`#b8cbd8`→`#ccd6dd`）中夹着楼体剪影，下方是建筑与树
- 分区域统计：森林上空**绿色占 69%**、平均色 (51,76,37) 是正常深绿；城区上空以建筑玻璃蓝灰为主
- 飞机在画面中的像素 (84,88,92) 与背景 (55,54,50) 差 105 → 确实画出来了

期间发现并修掉两个渲染问题：颜色贴图没标 `sRGBEncoding` 导致整幅画面被"抬高"一次而发白；追尾相机俯角过大，地平线跑到画面外。

## 6. 机身模型

`world.js` 的 `buildDrone()` 用基本几何体程序化拼出机身：压扁的椭球做上下两片外壳、锥台做电机座、`ExtrudeGeometry` 配合贝塞尔曲线做出带后掠的桨叶、机头下方是云台相机（支架 + 相机体 + 镜头）、两条支腿加两根滑橇。

**外观参考的是大疆消费级四轴的设计语言，不是大疆的模型或贴图**——没有任何外部资源文件，全部代码生成，因此也没有版权问题。四个 LED 的位置对应固件的四个机臂，颜色直接由固件灯控任务算出的引脚电平驱动。

模型按 **3 倍**绘制（`config.DRONE.visualScale`）。物理上这是一台 0.055 kg / 100 mm 轴距的微型四轴，按真实尺寸画的话在 6 米外只有二十来个像素，根本看不清姿态；放大后视觉尺寸接近 300mm 级的消费级机型，也正是外观参考的那一级。缩放只作用于渲染——模型的起落架底面被对齐到 group 原点，所以放大多少倍都仍然"踩"在地面上，动力学完全不受影响。

相机提供了三种**第三人称**视角（相机始终在机身外部）：

| 视角 | 相机位置 | 用途 |
| --- | --- | --- |
| 追尾跟随 | 机尾后上方，视线朝机头前方 | 常规飞行，地平线落在画面上三分之一 |
| 环绕 | 绕飞机任意角度，鼠标拖动 / 滚轮缩放 | 查看姿态与外观 |
| 俯视跟随 | 飞机上方偏后，往下看 | 在楼群里盯住飞机位置 |

### 6.1 坐标系与操控方向（一个容易踩的坑）

固件文档把世界坐标记成 **X=正北, Y=正东, Z=正上**。这个标法在 Z 轴朝上时是**左手系**：右手系要求 X→Y 从上往下看是逆时针，而"北→东"是顺时针。

three.js 和仿真里的物理用的都是标准右手代数，所以按左手系理解时，**渲染出来的画面是左右镜像的**：相机在机尾后方时，屏幕右方向对应世界 -Y。俯仰正好落在镜像的对称轴上，看起来正常；横滚和偏航则会反 —— 表现就是"按左键飞机往右飞"。

处理方式：仿真内部统一按物理上正确的右手系来记（**+Y 是机体左侧**，因为 Z×X 得到的那个轴，在机头朝北时指向西），再把差异在遥控器通道极性里配平：

```js
STICK_POLARITY: { THR: 1, YAW: -1, PIT: 1, ROL: 1 }
```

配平的判据只有一条：**推杆方向 = 飞机在屏幕上的运动方向**。

这条链路（摇杆 → 极性 → 组帧 → 空口 → 飞控解析 → 姿态环 → 物理）被 `tools/selftest.mjs` 第 11 节完整回归，6 个方向逐一断言，所以以后改极性或改相机参数如果把这个弄反了，自检会直接失败。

## 7. 与真机的差异

| 差异 | 影响 |
| --- | --- |
| 用双精度浮点（固件是单精度 float32） | 仿真里的数值漂移比真机小；固件依赖 float32 的饱和特性，而 JS 的 double 不会饱和，所以 `tasks.js` 里加了一个发散看门狗（检出 NaN 就复位姿态解算并计数），实测从未触发 |
| 桨叶气动只用了等效的推力/反扭矩/阻尼系数 | 没有挥舞、动态入流、地面效应，大机动与近地悬停的细节不准 |
| 加速度计只算重心处比力 | 未计入转动加速度在传感器安装位置上的分量 |
| 树没有碰撞体，激光不打树冠 | 可以穿过树，树冠上方不会触发定高的高度变化 |
| VL53L1X 只用"量程截断 + 白噪声 + 偶发丢包" | 没有真实芯片的距离状态码与串扰处理 |
| 链路是概率模型（距离衰减 + 遮挡 + 比特错误率） | 不是信道级仿真，但足以驱动断链保护与校验逻辑 |
| 固定 0.5ms 时间片 | 真机是抢占式调度，有任务切换与中断开销 |

## 8. 仿真里观察到的两个固件特点

这两条是**固件本身的行为**，仿真只是把它复现出来了：

### 8.1 切入定高时会有一次下沉

Z 轴速度估计用互补滤波：

```
zSpeed = 0.9·(上次 + (normAccZ − staticAcc)·dt) + 0.1·(height − heightPID.measure)/dt
```

第一次计算时 `heightPID.measure` 还是初值 0，于是位置项给出 `height/dt` 这个极大的"速度"，被 `zSpeedPID` 的 ±150 输出限幅后表现为一次明显的掉高；又因为互补滤波里加速度项占 0.9、记忆很长，这个错误估计需要约 2 秒才衰减掉，所以下沉会持续一段时间才恢复。

真机上有同样的现象。要改善的话，可以在进入定高时先把 `heightPID.measure` 初始化为当前高度（一行改动），或者缩短互补滤波的记忆。

### 8.2 定高环是纯比例的

`heightPID` 与 `zSpeedPID` 的 `ki` 都是 0，所以定高只能靠比例项把误差压小，没有积分项去消除残余偏差；同时稳态时 `zSpeedPID` 输出必须回到接近 0 才能和悬停油门配平。

想要更硬的定高，可以给高度环加一个较小的 I，并同时配好 `integralMin/integralMax`（`PID_Struct` 已经支持），改完用 `selftest.mjs` 的定高用例回归一下即可。

## 9. 想继续扩展的话

- **换物理参数**：直接改 `js/config.js` 的 `DRONE`，或者跑 `tools/tune.mjs` 重新整定
- **改控制参数**：`js/config.js` 里 `PID_POSTURE` / `PID_HEIGHT` 与固件 `App_Flight.c` 对应，可以在这里试新增益，稳定了再写回固件
- **加磁场**：`fw/imu.js` 用的是 Mahony 的六轴版本，加磁力计就是补上九轴那部分
- **换场景**：`world/layout.js` 是纯数据，改它就能换地图；高度场与碰撞会自动跟着变（渲染、物理、测距共用同一个 `terrainHeight`）
